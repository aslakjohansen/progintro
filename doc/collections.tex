\section{Sets}

% intro: definition
Borrowing from \idx{mathematics}{Mathematics}, a \defi{set}{Set} is a \idx{collection}{Collection} of \idx{distinct}{Distinct} objects. What matters is that any object is either in the set or not in the set. There is no notion of how many times an object is in the set; it either is or is not in it.

\subsection{Hash Sets}

% organization
A \defi{hashset}{Hash set} is a specific implementation of a set. Figure \ref{fig:collections:hash:set} illustrates how it is organized. As there can be a large (practically infinite) number of objects to be placed in a set, it is not \idx{feasible}{Feasibility} to simply \idx{enumerate}{Enumerate} all potential objects and use this as an index into an array. An array \textsl{is} being used, but it is far too small. Objects are mapped to indices in this array, but as the number of potential objects outnumber the indices there will be objects that are \idx{mapped}{Mapping} to the same index. That position in the array is also called a \defi{bucket}{Bucket}, and multiple objects may end up in the same one. To \idx{resolve}{Resolving} this conflict, a secondary mechanism is put into use: each entry of the array references a list of all the objects that are in the set and map to this index. Before adding an object to this list, one has to make sure that it is not already there.

\subsubsection{Hashing}

\defi{Hashing}{Hashing} is a process whereby a function is applied to a piece of memory (e.g., an object) in order to produce a hash code. That \defi{hash code}{Hash code} is essentially an integer. Ideally, any change in the object will change the resulting hash code.

\subsection{Operational Cost}

% lookup cost
In order to perform a \idx{lookup}{Lookup} (i.e., to see whether an object is in the set) the following operations need to be performed:
\begin{itemize}
  \descitem{Hashing} The object needs to be \idx{hashed}{Hashing} into an integer. This typically involved looping over every byte of the object. This is, however, something that we have control over.
  \descitem{Array Lookup} That integer is then used as an index into the array. This gives us the correct \idx{bucket}{Bucket} and costs us 1 \idx{addition}{Operation!Addition} and 1 \idx{memory access}{Operation!Memory access}.
  \descitem{Bucket Lookup} That bucket acts as the root of a \idx{linked list}{Linked list} that we have to \idx{search}{Search} through. For each element in the list (until we find our match or reach the end) we need to do a \idx{comparison}{Operation!Comparison} to check whether this object is equal to the one we are looking for. If the bucket contains $n$ objects then this will cost us $n$ memory accesses and $n$ \idx{function calls}{Operation!Function call} to functions that can determine \idx{equality}{Equality}.
\end{itemize}

% consequences
So, the main cost is determined by the size of the buckets. That size can be reduced by choosing a larger array. But a larger array will more frequently be wasted. So, we have a classical \idx{tradeoff}{Tradeoff}; at one end we have a single bucket and a lookup may end up costing 1 memory access and one function call to determine equality per element in the set, and at the other end we have a \idx{guarantee}{Guarantee} of one bucket per element with a lookup cost of one memory access and a size that consumes all of your memory. Neither end is attractive, so the tradeoff needs to be \idx{resolved}{Resolving} by balancing the positives and the negatives. Luckily, other people have done this for us.

% how does add and removal cost differ
An \idx{add operation}{Set!Add operation} makes sure that an element is in a set. To do that it needs to hash the object to find the right bucket, and then look through the list of the bucket until it finds either a match or the end of the list. In the latter case it needs to add the object. A \idx{removal operation}{Set!Remove operation} essentially works in the same way, but it removes on match and does nothing at the end of the list.

\subsection{Bounded Enumerable Values}

% how this special case fits into a bitvector
Remember that \defi{premise}{Premise} that meant that multiple objects would have to map to the same index of the array? That premise often doesn't hold. If our objects are continuously \idx{enumerable}{Enumerability} and \idx{bounded}{Boundedness} in number, then there is another implementation that is much more \idx{efficient}{efficient}. It is called a \defi{bitvector}{Bitvector}, and it is simply a sequence of bits. If a bit is set (aka, it has the true value) then the object that uniquely maps to the index of this bit in the set. If the number of potential objects is 201, then we need $201$ bits or $\lceil 201 \rceil = 26$ bytes to represent this bitvector. Modern processors implement \idx{bitwise boolean instructions}{Instruction!Boolean!Bitwise} that match each of the common \idx{set operations}{Set!Operation on}.

% pros
This implementation is much more \idx{compact}{Compactness} in terms of space, and a lookup only costs us a single \idx{memory access}{Memory access} instruction and no \idx{function calls}{Function!Call}.

\section{Maps}
\label{collections:maps}

% etymology: maps of the world, no perfect fit for a (mostly) spherical world, projections of physical features of the globe to a flat piece of paper (or screen), this we call a mapping from A to B, mappings exists everywhere in software, example of a shopper and a shopping cart
Let's take a stroll down the \idx{etymology}{Etymology} of \idx{maps}{Map}. We have all seen different kinds of maps of the world; some depict altitude, others politics or climate. But our planet is (mostly) spherical, yet most of our maps are designed for a flat (\idx{planar}{Planarity}) surface. There is no perfect way of \idx{projecting}{Projection} the globe onto a flat surface, and so we have come up with projections that have attractive \idx{qualities}{Qualities} and acceptable \idx{flaws}{Flaws} for certain uses. For instance, the \idx{Mercator projection}{Projection!Mercator} is useful for \idx{navigation}{Navigation} and the \idx{Robinson projection}{Projection!Robinson} represents a visually pleasing compromise of most qualities. The notion of associating something (e.g., a position) with something else (e.g., an altitude) is called a \defi{mapping}{Mapping}, and a construct that does this for a \idx{set}{Set} of elements is called a \defi{map}{Map}. Accordingly, each projection represents a mapping from a flat surface to the face of the planet. Mappings exists everywhere in software. If we push the definition a bit, a \typename{float[]} is a mapping from integers (i.e., the \idx{indices}{Index}) to \typename{float} values. For a more application-oriented use, we need look no further than an \idx{online shop}{Online shop}; it will at all time have a map from \idx{users}{User} to \idx{shopping carts}{Shopping cart}. Whenever a user adds something to their cart in the \idx{browser}{Browser}, the code on the server side looks up the cart that the user maps to and updates it. In computing we refer to the \idx{identifier}{Identifier} used to look up something as the \defi{key}{Map!Key}, and the something that is being looked up as the \defi{value}{Map!Value}. We say that the key \idx{maps}{Mapping} to the value.

% no natural representation
In order to produce a data structure that implements a map we need to find a way of storing it in memory. That part was easy for an \idx{array}{Array} as the mapping from \idx{index}{Index} to memory location was \idx{linear}{Linearity} and \idx{compact}{Compactness} in nature and thus \idx{trivial}{Triviality}. A map can be indexed by anything (e.g., a \classname{Person}) in order to get something (e.g., an \classname{Address}). The fact that we need to be able to index it using anything means that it doesn't clearly map to the way \idx{main memory}{Memory!Main} is organized.

% hacking our way around it: array of pairs
So, let's for a moment not care about how the data are laid out in memory and come up with a \idx{naive}{Implementation!Naive} implementation. In this implementation, we introduce the notion of a key and value pair, and the \say{map} is quite simply a list of these. We introduce methods for adding and removing key and value pairs that ensures that no key is present more than once. The code for this can be found in figure \ref{fig:collections:map:arrayofpairs}. We can further add a method for looking up the value associated with a specific key. This method would \idx{search}{Search} through all the elements of the list until the key was found and then return the matching value. This works. But remember how an array lookup \idx{cost}{Cost} us an \idx{addition}{Operation!Addition} and a \idx{memory access}{Operation!Memory access}? What is the equivalent price of looking up a key in this map implementation? In the worst case -- and this is often what we care about -- we need to call the \methodname{Equals} method on each element of the array. Without going into details on the cost of calling a method on an object, we can clearly say that some amount of \idx{work}{Work} has to be done per object. If the list contains $n$ objects we need to do variants of that work $n$ times. In other words, the more mappings our map contains, the more expensive it is to look up something. Compare that to the array where the cost was fixed (and relatively small). This is an inconvenient property of our implementation. It is, however, not that bad; had no better solutions been found, we would have used this implementation.

% terminology: associative array (same), dictionary (mostly same), hash table (concrete implementation of a map)
Maps are also called \idx{associative arrays}{Associative array}, and \idx{dictionaries}{dictionary}. Dictionaries, however, have historically been a broader term spanning \idx{data structures}{Data structure} other than maps. These terms define the data structure at an abstract level: \idx{keys}{Key} are \idx{unique}{Uniqueness} and associated with a \idx{value}{Value}, and associations can be \idx{inserted}{Insertion}, \idx{updated}{Update} and \idx{removed}{Removal}. They don't say anything about how they are \idx{implemented}{Implementation} though. A hash table is a common implementation of a map. In the next section, we will explore hash tables.

\subsection{Hash Tables}

% intro
The most common implementation of a map is that of a hash table. Here, keys are hashed to an integer which is then used as an index into an array that references a linked list of a key+value combination. This is essentially the same setup as a hash set except that the linked lists contain both keys and values. Figure \ref{fig:collections:hash:table} illustrates this concept. The key has the exact same function as the object reference in the hash set but the common operation is to look up the value associated with a key. That is, find the location of the key and then return the the value stored in the same chain link.
