\chapter{Testing}

% intro: Boeing 747
A longs time ago, \idx{Boeing}{Boeing} was known for making products of exceptional engineering and quality. The best example of this is likely the \idx{Boeing 747}{Boeing 747}; the original \say{Jumbo Jet}. This \idx{airplane}{Airplane} was such a leap forward that the media hailed it as a revolutionary engineering achievement. Test pilots remarked that it -- despite its massive size -- \say{landed itself}. It contained 274km of \idx{wires}{Wire} and was made up of six million physical \idx{components}{Component}. And the truely remarkable thing was that it worked \idx{reliably}{Reliability}.

% complexity compared to software
Six million components that need to work together. That certainly is a lot of complexity. But, if we look past the fact that these components still need to work together as they \idx{age}{Aging}, these are actually quite small numbers compared to what we see in software. Not that this can ever be an apples-to-apples comparison. Unlike software, airplane parts degrade over time. On the other hand, when an airplane component is degraded or faulty, it will often be easy to detect visually. Bugs in software exists precisely because they have avoided detection.

\section{Purpose}

% why we test
Given the sheer \idx{complexity}{Complexity} of software systems and the lack of obvious \idx{indicators}{Indicator} of \idx{faults}{Fault}, the need for dealing with faults is different in nature. For starters, testing -- the act of checking whether some functionality behaves as \idx{specified}{Specification} -- is done entirely before the product is \idx{shipped}{Shipping!Of product}.

% test case
\idx{Testing}{Testing} is performed by evaluating so-called \defi{test cases}{Test case}. These are concrete \idx{scenarios}{Scenario} that are well-described in terms of the intended \idx{outcome}{Outcome}. That scenario usually covers a small subset of \idx{functionality}{Functionality}. While it may not be \idx{packaged}{Packaging} as such, that functionality has the \idx{interface}{Interface!Of functionality} of a function. To activate that \say{function}:
\begin{enumerate}
  \item The \idx{evaluation}{Evaluation} happens in a \idx{context}{Context} with well-defined \idx{state}{State}. This must first be \idx{setup}{Setup}.
  \item The function needs concrete \idx{values}{Value}. The combination of this and the context is the scenario.
  \item After evaluation of the function, we observe both the \idx{return value}{Return value} and the the context (which may have been \idx{transformed}{Transformation}).
\end{enumerate}

% choosing test cases
The test cases are chosen in such a way that they \idx{cover}{Coverage} the factors that influence the function and test that the \idx{effects}{Effect} that they produce match our perception of what is correct \idx{behavior}{Behavior!Of functionality}. A well-designed test case is one whose results provide valuable insight into the \idx{quality}{Quality} and behavior of the code.

% test suites
As we rarely use software in as narrow situations as can be covered in a single test case, there is a need for a collection of test cases; a \defi{test suite}{Test suite}. A test suite should be comprehensive enough to provide the \idx{evidence}{Evidence} needed to argue that the code is probably (relatively) \idx{correct}{Correctness}. When we \idx{run}{Test suite!Running} a test suite, it will tell us which test cases \idx{pass}{Test case!Passing}, and which \idx{fail}{Test case!Failing}. By looking at how that changes after a \idx{modification}{Modification} of our \idx{codebase}{Codebase}, we can reason about which \idx{bugs}{Bug} this update \idx{fixed}{Bug!Fix of} and whether it \idx{introduced}{Bug!Introduction of} new ones. That, of course, is only true to the \idx{granularity}{Granularity} and correctness of our test suite.

\section{Impossible Completeness}

% present base case
Let's define a functionality that is simple, but nontrivial. This can be concretized as a function that takes a \typename{sbyte} as parameter, adds the value \valuename{1} to it and returns the result. We could call that function \funcname{incr}.

% how to test it
To ensure \idx{correctness}{Correctness}, we must verify that all possible inputs produce the correct output. As a \typename{byte} can take on $2^8=256$ different values, we need 256 test cases. That is a lot of work, but it can be done. The job of defining these test cases requires concentration though. A mistake in a test case can easily cause an \idx{bug}{Bug} to remain undetected.

% scalability issue
But, what if the \idx{parameter}{Parameter} was a 64 bit or -- gods forbid -- a 128 bit integer? A 128 bit integer value can take on $2^{128}=3.4 \cdot 10^{38}$ different values. This is by almost all \idx{metrics}{Metric} a very large number. How large a number? There are $3.34 \cdot 10^{38}$ \idx{electrons}{Electron particle} in a cubic kilometer of \idx{water}{Water}. So, if we are able to store every test case in a single electron -- something not allowed by our current understanding of \idx{physics}{Physics} -- then we will need approx $1km^2$ of water simply to store these test cases. If we instead have two such integers as parameters, then we would need $2^{128 \cdot 2}$ electrons to store all the test cases, and this is dangerously close to the number of electrons in the known \idx{universe}{Universe}. This \idx{approach}{Approach} clearly does not \idx{scale}{Scalability}.

\section{Boundary Cases}

% leadup
As it is intractable to test all cases, we need a different approach; one that trades completeness for test execution efficiency. In short, we need to pick a limited subset of the possible inputs, and test these. But which subset do we pick? We could randomly select $n$ inputs and test these. But how do we pick one $n$ over another? If or \funcname{incr} function works correctly for an input of 12 why wouldn't it also work for a value of 13?
