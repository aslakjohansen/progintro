\section{Purpose}

% why we test
Given the sheer \idx{complexity}{Complexity} of software systems and the lack of obvious \idx{indicators}{Indicator} of \idx{faults}{Fault}, the need for dealing with faults is different in nature. For starters, testing -- the act of checking whether some functionality behaves as \idx{specified}{Specification} -- is done entirely before the product is \idx{shipped}{Shipping!Of product}.

% test case
\idx{Testing}{Testing} is performed by evaluating so-called \defi{test cases}{Test case}. These are concrete \idx{scenarios}{Scenario} that are well-described in terms of the intended \idx{outcome}{Outcome}. That scenario usually covers a small subset of \idx{functionality}{Functionality}. While it may not be \idx{packaged}{Packaging} as such, that functionality has the \idx{interface}{Interface!Of functionality} of a function. To activate that \say{function}:
\begin{enumerate}
  \item The \idx{evaluation}{Evaluation} happens in a \idx{context}{Context} with well-defined \idx{state}{State}. This must first be \idx{setup}{Setup}.
  \item The function needs concrete \idx{values}{Value}. The combination of this and the context is the scenario.
  \item After evaluation of the function, we observe both the \idx{return value}{Return value} and the the context (which may have been \idx{transformed}{Transformation}).
\end{enumerate}

% choosing test cases
The test cases are chosen in such a way that they \idx{cover}{Coverage} the factors that influence the function and test that the \idx{effects}{Effect} that they produce match our perception of what is correct \idx{behavior}{Behavior!Of functionality}. A well-designed test case is one whose results provide valuable insight into the \idx{quality}{Quality} and behavior of the code.

% test suites
As we rarely use software in as narrow situations as can be covered in a single test case, there is a need for a collection of test cases; a \defi{test suite}{Test suite}. A test suite should be comprehensive enough to provide the \idx{evidence}{Evidence} needed to argue that the code is probably (relatively) \idx{correct}{Correctness}. When we \idx{run}{Test suite!Running} a test suite, it will tell us which test cases \idx{pass}{Test case!Passing}, and which \idx{fail}{Test case!Failing}. By looking at how that changes after a \idx{modification}{Modification} of our \idx{codebase}{Codebase}, we can reason about which \idx{bugs}{Bug} this update \idx{fixed}{Bug!Fix of} and whether it \idx{introduced}{Bug!Introduction of} new ones. That, of course, is only true to the \idx{granularity}{Granularity} and correctness of our test suite.

\section{Test Types}

% intro
Larger \idx{projects}{Project} will make use of elaborate \idx{test strategies}{Test!Strategy} that test the \idx{codebase}{Codebase} at different \idx{granularities}{Granularity}. It is common for a test strategy to involve the following test types:

\begin{itemize}
  \descitem{\defi{Unit Testing}{Unit test}:} Code is divided into small units and test them individually. Within the \idx{object-oriented paradigm}{Paradigm!Object-Oriented}, there is typically a one-to-one mapping between \idx{methods}{Method} and the context in which they are called (the \idx{unit}{Unit}). Typically we group them by \idx{class}{Cæass}. Each method is thus tested \say{independently} of the others, and this is typically done by performing a number of specific, well-defined \idx{test cases}{Test case}. However, since classes often depend on each other, unit testing alone is usually not sufficient. That is why we perform:
  \descitem{\defi{Integration Testing}{Integration test}:} After verifying that the individual units work independently, it’s time to ensure that the \idx{interfaces}{Interface!Between functions} between them function correctly. Here, one will typically -- for reasons of clarity -- choose to consider a \idx{subsystem}{Subsystem} at a time. Figure \ref{fig:test:integration} illustrates what such subsystem coverage could look like.
  \descitem{\defi{System Testing}{System test}:} When all subsystems are tested to be correct, a system test is performed. This is like an integration test but focuses on the entire \idx{system}{Sytem!In software engineering} rather than specific subsystems. This allows us to catch \idx{errors}{Error} that first appear when examining \idx{behavior}{Behavoir!Informal} between the (integration)test subsystems or when all subsystems work together.
  \descitem{\idx{Acceptance Testing}{Acceptance test}} the final test against the customer's \idx{requirements}{Requirement} and/or \idx{program specification}{Program specification} that determines whether the product can be \idx{delivered}{Delivery}. The focus is often on the final \idx{functional}{Requirement!Functional} and \idx{non-functional}{Requirement!Non-functional} requirements, and these relate to the system as a whole. This type of testing is independent of the \idx{implementation}{Implementation}. \idx{Correctness}{Correctness} is typically assumed.
\end{itemize}

\section{Impossible Completeness}

% present base case
Let's define a functionality that is simple, but nontrivial. This can be concretized as a function that takes a \typename{sbyte} as parameter, adds the value \valuename{1} to it and returns the result. We could call that function \funcname{incr}.

% how to test it
To ensure \idx{correctness}{Correctness}, we must verify that all possible inputs produce the correct output. As a \typename{byte} can take on $2^8=256$ different values, we need 256 test cases. That is a lot of work, but it can be done. The job of defining these test cases requires concentration though. A mistake in a test case can easily cause an \idx{bug}{Bug} to remain undetected.

% scalability issue
But, what if the \idx{parameter}{Parameter} was a 64 bit or -- gods forbid -- a 128 bit integer? A 128 bit integer value can take on $2^{128}=3.4 \cdot 10^{38}$ different values. This is by almost all \idx{metrics}{Metric} a very large number. How large a number? There are $3.34 \cdot 10^{38}$ \idx{electrons}{Electron particle} in a cubic kilometer of \idx{water}{Water}. So, if we are able to store every test case in a single electron -- something not allowed by our current understanding of \idx{physics}{Physics} -- then we will need approx $1km^2$ of water simply to store these test cases. If we instead have two such integers as parameters, then we would need $2^{128 \cdot 2}$ electrons to store all the test cases, and this is dangerously close to the number of electrons in the known \idx{universe}{Universe}. This \idx{approach}{Approach} clearly does not \idx{scale}{Scalability}.

\section{Boundary Cases}

% leadup
As it is \idx{intractable}{Tractability} to test all cases, we need a different \idx{approach}{Approach}; one that \idx{trades}{Tradeoff} \idx{completeness}{Completeness} for test execution \idx{efficiency}{Efficiency!Of test execution}. In short, we need to pick a limited \idx{subset}{Subset} of the possible \idx{inputs}{Input}, and test these. But which subset do we pick? We could \idx{randomly}{Random selection} select $n$ inputs and test these. But how do we pick one $n$ over another? If or \funcname{incr} function works correctly for an input of 12 why wouldn't it also work for a value of 13? We have no reason to suspect that \funcname{incr} behaves differently on an input of 12 than it does on an input of 13. Given that the type of the input is an integer, with this class of types comes the the possibility of an \idx{overflow}{Overflow} and an \idx{underflow}{Underflow}. As deviate from our normal perception of \idx{arithmetic operations}{Operation!Arithmetic}, it is common for \idx{bugs}{Bug} to be linked to them. These happens at the two ends (aka bounds) of the range that can be represented, and because of that we refer to them as \defi{boundary cases}{Boundary case} (or \idx{edge cases}{Edge case}). We could potentially add zero to these as it can be difficult to reason about the outcome of dividing by zero.

\section{Formal Verification}

Testing every single \idx{scenario}{Scenario} is a hopeless endeavor. \idx{Formal verification}{Verification!Formal} offers an alternative: Instead of executing parts of our code to experimentally evaluate how it behaves, we can analyze the program \idx{statically}{Analysis!Static} and, based on this, draw \idx{conclusions}{Conclusion} about which \idx{guarantees}{Guarantee} we can provide. A static analysis is an analysis that is performed without evaluating the execution of the code.

This process is considerably more difficult. To simplify it, we often create a (hopefully) \idx{equivalent}{Equivalence} model of our code that is easier to analyze. However, in doing so we also introduce the possibility of introducing additional errors. In \idx{safety-critical}{System!Safety-critical} systems, however, this \idx{tradeoff}{Tradeoff} is often considered worthwhile.

\section{Performance Evaluation}

% intro: testing tries to find ways in which the implementation fails to function correctly, but correctness is rarely enough for us to claim that the implementation fulfills its the requirements, functional requirements can often be mapped to correctness, non-functional ones -- on the other hand -- rarely can, many non-functional requirements are performance related, for instance (i) [response time] when a user activates a functionality the result of that functionality should be visible within 10 seconds, (ii) [memory consumption] During operation the system should use no more than 300MB of main memory, and (iii) [throughput] the system should be able to process at least 20 elements per second.

% the act of evaluate the performance of a system is called performance evaluation, it has its roots in experimental computer science, the excellent "the art of performance evaluation" book takes the reader through the necessary steps, performance evaluation is complex and time consuming task, in this book we distill it into the following summary

% the summary: to evaluate the performance of a system we measure key performance indicators (KPIs) while exposing the system to relevant workloads. That is, we operate the system under interesting conditions with real or simulated users. Some of the KPIs -- like memory and CPU consumption -- can be extracted from the operating system. Others will have to be extracted by instrumenting the codebase. That is, modifying it so that certain classes, in addition to fulfilling its normal role, also collect KPIs. This is the case for response time. Often, the codebase has a lot of configuration parameters like buffer sizes and timeouts. To explore how these affect the performance of a system, we test the performance of different parameter configurations.
