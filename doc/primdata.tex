Keeping track of a single value is trivial. But once you start having a handful of values to juggle, you begin to feel a burden. Yet, by following \idx{good practices}{Practice!Good} for naming your variables, it shouldn't be a big deal. However, as the number of values that we need to deal with grow, that solution model starts to break down. Imagine a program that we are writing a program that has to do some sort of analysis on the historical daily temperatures some calendar year. That is 365 (or 366) values right there, and that isn't even a remotely large number of values. Even with a good \idx{naming convention}{Convention!Naming}, keeping track of that many variables will be a mess. But it doesn't stop there: Some values are related and we often have to treat them that way. In this chapter we look into how we can structure data in ways that allows us to reason about much larger number of values through code. This is a form of \idx{scalability}{Scalability}.

\section{Complex Types}

% atomic types: types that cannot meaningfully be subdivided further, yes an int can be split into bits but why would I care if the 7th bit is set? it gets a bit more murky with floats, here I might want to look into the sign or the magnitude (exponent), but all the float instructions of our processor operate at the unit of a float, so atomic is an apt qualifier for such types (real atoms also consists of smaller elements), in \csharp\ they are called primitive
Primitive types cannot meaningfully be subdivided further. Yes, an \typename{int} can be split into bits, but why would I care what the value of the 7th bit is. It gets a bit more murky with floats. Here, I might want to look into the sign or the magnitude (i.e., the exponent). But all the floating-point instructions of our processor operate at the unit of a full floating-point value (i.e., sign, mantissa and exponent). So, atomic is an apt qualifier for such types. After all, real \idx{atoms}{Atom} also consists of smaller elements. In \csharp, such types are called \defi{primitive}{Type!Primitive}.

% complex types: complex types are are complexes of data, they contain (or at least may contain) multiple elements of data, these data can in turn be atomic or complex, those complex types can arrange and expose their elements in different ways, this chapter will cover the most basic variations, because these types structure data we call them datastructures
Complex types are complexes of data. They contain (or at least may contain) multiple elements of data that can in turn be atomic or complex. Those complex types can be used to arrange and expose these elements in different ways. This chapter will cover the most basic variations. Because these types structure data, we call them \defi{datastructures}{Datastructure}.

\section{Reference Types}

% problem: from the compilers point of view atomic types are easy to work with, an atomic type fits into a register and can be read from and written to memory through a single operation, a complex type on the other hand does not fit into a single register, and so the compiler has to decide how large a part of the data needs to be loaded from memory to registers how and how much needs to be written back after we are done with it, later on you will learn that multiple things can go on at the same time within the same program, so the implementation of this needs to ensure that a consistent view of the data is presented to all these ongoing things
From the \idx{compilers}{Compiler} point of view, atomic types are easy to work with. They fit into a \idx{register}{Register}, and can be read from and written to \idx{memory}{Memory} in a single operation. Choosing one of two values is trivial. A complex type, on the other hand, does not fit into a single register, and so the compiler will have to decide how large a part of the data needs to be loaded from memory into registers, and how much needs to be written back after we are done with it. Later on, you will learn that multiple things can go on at the same time within a single program. When this happens, the implementation of this needs to ensure that a consistent view of the data is presented to all of these ongoing things.

% solution (ref type): references do fit into a single register, variables of reference types holds the reference (address) and not the value, two variables may refer to the same data (by holding the same reference), nothing changes with respect to the data being referenced, it still doesn't fit into a single register, but copying the reference is a trivial and fast operation
A reference is an \idx{address}{Address!Memory} (in memory) to some datastructure, and such a reference can be used as a value. References are atomic values and do fit into a single register. Variables of reference types thus hold the reference (i.e., the address) and not the value (i.e., the datastructure). Two reference type variables can refer to the same data. All it takes is for them to hold the same address. Nothing changes with respect to the data being referenced: It still doesn't fit into a single register. But we now have the option of copying references, and that operation is both trivial and fast.

% solution (acceptance): another solution is simply to accept that the datastructure cannot be represented in a single register and deal with the complications that stem/arise from that, this is essentially what you have done so far if you have had two related variables and you needed to make a copy of the combination, luckily those complications are usually handled by the compiler, \csharp choices
Another solution is simply to accept that datastructures cannot be represented in a single register, and deal with the complications that arise from that. This is essentially what you have done so far when you had two variables and needed to make a copy of that combination. Luckily, those complications can be handled by the compiler. So, while making datastructures reference types is the natural choice, they can also be made value types. \csharp\ offers mostly reference type datastructures, and these are the ones we will be focusing on.

% summary
So, types where a variable is mapped to hold values in register(s) are called \idx{value types}{Value type}, and types where variable is mapped to hold a reference to an address in memory is called a \idx{reference type}{Reference type}. Copying a reference type copies the reference, and any modification to whatever it refers to is visible through all reference copies to these data.

\section{Nullability}

% backstory
On a traditional \idx{machine}{Machine}, the lowest \idx{addresses}{Address} have specific purposes, and most programs are not allowed to access them. Address zero specifically is an address what we should never try to read. Because of this, it has become convention to use this address to indicate an \idx{invalid}{Value!Invalid} value. This could be for uninitialized references or simply to indicate that something isn't present. It has become so common that many languages have introduced a keyword to represent this address and thus make it easier to spot. In \csharp, that keyword is \defi{\valuename{NULL}}{NULL@\directivename{NULL} reference}. In some other languages it is \defi{\valuename{nil}}{nil@\directivename{nil} reference}. All reference types in \csharp can be set to \valuename{NULL}. Following such a reference will cause an \idx{exception}{Exception} to be thrown and -- if \idx{uncaught}{Exception!Uncaught} -- \idx{crash}{Crash} the \idx{virtual machine}{VM}. More on exceptions in section \ref{sec:exceptions}. For now, just don't follow them. As it turns out, that is easier said than done.

% value types
In \csharp it was decided to pair every value type with a matching type that is \defi{nullable}{Nullability}. That is, they can represent every value the original type can represent, but also \valuename{NULL}. These types have extended the name of the original type with a question mark. For instance the type \typename{int?} is an \typename{int} that can also represent the value \valuename{NULL}. As this makes the value slower to work with, it is rarely used. Normal casting rules apply: One can cast implicitly from \typename{int} to \typename{int?} because we can do so without loosing information. If we want to go in the other direction, then there is no good way of representing the \valuename{NULL} value, and it thus requires an explicit cast to signal that we -- as the programmer -- is aware of the danger.

Let's start with an example. We need to create a program that helps us navigate a house. For this we need to model the concept of a door. \subsection{Colors}
% TODO: Move to functions as a case?

% light as a spectrum
\defix{Light} is made up of photons, and each \idx{photon}{Photon} has a wavelength. The \defi{wavelength}{Wavelength} of the photons determines which color our eyes will observe. A wavelength of 380nm is \idx{violet}{Violet} and one of 740nm is \idx{red}{Red}. In between these you have all the colors of the \idx{rainbow}{Rainbow}, in the order of the rainbow. Coincidence? Just outside of the \idx{visible spectrum}{Spectrum!Visible}, you will find \idx{infra-red}{Infra-red} and \idx{ultra-violet}{Ultra-violet}. Our eyes are, however, constantly bombarded by photons, so in reality we always observe a distribution across this spectrum. Our \idx{eyes}{Eye}, though only has three (or four) tunings of receptors. These, roughly corresponds to red, green and blue. So, your eyes (and \idx{brains}{Brain}) need to do a lot of interpretation.

% computer representation
In a computer, colors are typically \idx{represented}{Representation!Color} using three values; one for red intensity, one for green intensity, and one for blue intensity. That somehow matches the model of our eyes \ldots\ We say that these are the \textsl{components} of the color. There is a number of ways to express such an \idx{intensity}{Intensity}. It seem natural to use a number between 0 and 100, or perhaps a number between 0.0 and 1.0. However, due to the way processors work on integers, these boundaries are not particularly special. Typically, a byte is use to represent each component of the color. That means that we have the ability to express $2^8=256$ different intensities of each component, or a total of $256^3=16777216$ different colors. The value zero is used to represent complete \idx{darkness}{Darkness}. Full intensity is then the value 255.

\section{Sequences in Data}

% intro: rooting in structs, structured data are laid out in sequence, every element can be named through a field name, two consequences follow from this (1: we need to define a name for each element at compiletime, 2: doing something with every element requires us to keep track of the order through other means)
Structured data are laid out in sequence, and every \idx{element}{Sequence!Element} can be named through a symbolic field name. For many purposes, this is great. It does, however, have two consequences that will at times work against us. Those are (i) that we need to have explicitly defined a name for each field at \idx{compile time}{Compile time}, and (ii) that doing something with every element requires us to keep track of the order of those names through other means.

% indexed quality: addressing individual elements through symbolic names certainly has its advantages, imagine a company that stores doors, one day they may have 80 doors in stock, but we certainly don't want to create symbolic names for each of these, then we would have to update our code every time a door is shipped or a new shipment is received, what we are looking for is an indexed data structure, that is a datastructure that contains element that can be named through an integer value (that typically represents its position in that structure), the ability to do so allows us to loop over all elements of the structure and that is -- as we will see -- an extremely useful ability
Addressing individual elements through symbolic names certainly has its advantages. But this is not always the case. Imagine a company that stores doors. One day they may have 80 doors in stock. We certainly don't want to create symbolic names for each of these. Then we would have to update our code every time a door is shipped or a new shipment of doors have arrived. What we really want is for us to be able to express our code is such away that it automatically adapts as the stock fluctuates. To achieve this \idx{quality}{Quality}, we need an \defi{indexed datastructure}{Indexed datastructures}. That is, a datastructure that contains elements that can be named through an integer value (that typically represents its position in that structure). The ability to do so allows us to loop over all elements of the structure and that is -- as we will see -- and extremely useful ability.

\subsection{Arrays}
\label{sec:data:array}

% definition: array is a simple datastructure in which elements of the same size is laid our contiguously in memory, figure \ref{fig:data:array:alloc} illustrates this, accordingly given a pointer (address) to (the beginning of) the array, an index and an element size we can find the address of an element by
An array is a simple datastructure which contains zero or more elements of the same size. These elements are laid out contiguously in memory as depicted in figure \ref{fig:data:array:alloc}. Given a pointer to an array (i.e., the \idx{address}{Address} of the beginning of the array \idx{allocation}{Allocation}) $p$, an index within that array $i$ and a an element size $s$, we can find the address of that element by:

\begin{figure}[tbp]
  \input{figs/data_array_alloc.tex}
  \caption{The positioning of an array in memory.}
  \label{fig:data:array:alloc}
\end{figure}

\begin{alignat*}{1}
  \mathrm{index}(p,i,s) &= p + i \cdot s
\end{alignat*}

% calculation, this is why most languages agree that arrays start at zero
Notice how the first element of the \idx{memory space}{Memory space} is at index zero. This is why most common language agrees that indices for arrays start at zero. That is, the first element is element zero. Such arrays are sad to use \idx{0-based indexing}{0-based indexing@\valuename{0}-based indexing}. Other languages have decided that the first element of an array is element 1. These array are said to use \idx{1-based indexing}{1-based indexing@\valuename{1}-based indexing}. For a \idx{human}{Human} -- like those doing the actual programming -- 1-based indexing feels more natural: Most \idx{non-programmers}{Non-programmer} will have trouble relating to a reference the 0$^\mathrm{th}$ element and yet it is quite common for programmers to do so. To downside to 1-based indexing is that the above formula doesn't work. Using it results in an \idx{off-by-one error}{Error!Off-by-one}. So, the \idx{language designers}{Language designer} are left with a choice: Either \idx{offset}{Offset} the address so that it references a part of memory that is technically outside of the allocation (by one address), or add the cost of an extra subtraction operation every time the array is \idx{indexed}{Array!Indexing operation}.

As we have seen, there are two ways of initializing an array: Either it is explicit (we provide the concrete values), or it is implicit (and the \idx{default}{Default value} -- \idx{zero}{Zero value} -- value on the enclosed type is used). The implicit form can be followed by a series of a statements that assign individual values. In short, there are a number of ways to skin this \idx{cat}{Cat}. Someone went through the \idx{effort}{Effort} of adding more than one way of doing this. That usually doesn't happen without a reason. So, when should you use one over the other? Generally, the order is:
\begin{enumerate}
  \item If you have a guarantee that all elements will be overwritten before being read, and the \idx{compiler}{Compiler} will let you get away with it without producing \idx{warnings}{Warning} or \idx{errors}{Error}, then you can implicitly zero-initialize the array. This would be the case if, for instance, you are going to fill it up with data from a \idx{file}{File}.
  \item If there is some well-defined underlying structure, then you zero-initialize the array and use code to express that structure. This would be the case when, for instance, every element should be twice as large as the previous one. A for loop would then likely be used to do the actual initialization. Then the \idx{intention}{Intention} behind the sequence of values is expressed.
  \item If you have a small number of concrete values then you explicitly state them. There is some \idx{elasticity}{Elasticity} in this rule: How many are too many? The downside of explicitly listing the individual values are twofold. Firstly, these are \idx{hardcoded}{Hardcoding} values, they are hard to change, and because of that they are hard to \idx{test}{Testing} and \idx{debug}{Debugging}. For testing and debugging, it is beneficial to be able to test smaller and more clearly defined variants of the code. Secondly, it takes up space on the screen. If it fits on a single line, then great! If you can have one element per line and fit all the lines on a screen, then maybe. If you have to \idx{scroll}{Scrolling} to get an overview then the \idx{code quality}{Code quality} suffers.
\end{enumerate}

\subsubsection{Multidimensional Arrays}

% intro
We have seen how we, be nesting arrays, can a two-dimensional datastructure; a grid if you will. Isn't that a 2d array (and thus a multidimensional array)? Not quite. It is a complex of arrays that represent a multidimensional data structure. That appears to be a fairly weak -- and perhaps even unclear -- difference. Why make the distinction? Because we have a \textsl{different} concept that is called \defi{multidimensional arrays}{Array!Multidimensional}. Let's look into how they work, and -- by extension -- how they are different.

% layout of a 2d array
From the outside multidimensional arrays are very similar to nested arrays. You provide an \idx{index}{Index} per \say{dimension} and then you get a value that you can read or write. But the way the data are laid out in memory is quite different. Remember from figure \ref{fig:data:array:nest:square} How a rectangular nested array is laid out: The \idx{outer}{Array!Outer} array contains \idx{references}{Reference} to the \idx{inner}{Array!Inner}. Figure \ref{fig:data:IIDarray:layout} shows how a three row by four column multidimensional array is laid out in memory. Notice the complete lack of references? Those references are what allows for  \idx{jagged}{Array!Jagged} arrays and shared inner arrays.

\begin{figure}[tbp]
  \input{figs/data_2darray_layout.tex}
  \caption{The memory layout of a 2d array.}
  \label{fig:data:IIDarray:layout}
\end{figure}

% indexing
But following references takes \idx{time}{Time}. For each dimension of a nested array we have to follow one reference in addition to the formula from section \ref{sec:data:array}. In a 2d (multidimensional) array, the formula is:

\begin{alignat}{1}
  \label{f:data:marray:i}
  \left(
    \begin{array}{c}
      x \\
      y
    \end{array}
  \right)
  &= 
  \left(
    \begin{array}{c}
      \textcolor{teal}{i} ~\mathrm{mod}~ width \\
      \lfloor \textcolor{teal}{i} / width \rfloor
    \end{array}
  \right)
  \\
  \label{f:data:marray:xy}
  i &= \textcolor{teal}{y} \cdot width + \textcolor{teal}{x}
\end{alignat}

% followup
This is in essence a \idx{mapping}{Mapping} between the 2d integral coordinate system and a normal single-dimensional array! Given an index $i$ in the normal array, the corresponding $x$ and $y$ positions can be calculated according to formula \ref{f:data:marray:i}. More importantly, given an $x$ and a $y$ coordinate, the corresponding $i$ coordinate can be calculated according to formula \ref{f:data:marray:xy}.

% indexing compared to nested array
That is an addition and a multiplication. Two cheap (in terms of evaluation time) operations. There are no references to follow (except for the one to the hosting array). These formulas gain complexity as we increase the number of dimensions, but no more that the corresponding cheap operations from the nested array variant. In summary, representing $n$ dimensional data using nested arrays will require us to follow $n$ references to reach an element, but representing it using a multidimensional array will only require us to follow $1$ reference. In theory, for $n=1$ both the representation and the evaluation speed are exactly the same.

\subsubsection{Nesting vs Multiple Dimensions}

Everywhere we can use multidimensional arrays, we can also use nested arrays. Multidimensional arrays are faster (as in execution) to work with, but they are also less flexible. The flexibility advantage of nested arrays cover:
\begin{itemize}
  \item The ability to represent irregular sizes.
  \item The ability to share parts of the data structure. This benefits memory consumption directly, and at times the \idx{readability}{Readability} of the data \idx{modeling}{Data modeling}.
  \item The ability to make parts of the space \idx{nullable}{Nullability}.
\end{itemize}

\subsection{Linked Lists}
\label{sec:primdata:sequence:list}

% intro
Like arrays, \defi{linked lists}{Linked List} also implements sequences of data. The way they do so, however, is very different. An array is a single \idx{allocation}{Allocation} of a contiguous region of \idx{memory}{Memory}. Within this region of memory, the elements are laid out one after the other in order of their index. A linked list is made up of \idx{links}{Linked list!Link} containing a payload and a \idx{reference}{Reference} to the next link. The sequence is terminated by a \idx{\valuename{null}}{null@\valuename{null}} reference. These links can be scattered all around memory, and if one links reference points to an earlier link in the chain then the length of the chain is infinity (or \idx{MAXINT}{MAXINT@\textsl{MAXINT}} for whichever type you use for indexing it). Figure \ref{fig:primdata:linkedlist} illustrates a linked list with three elements; \say{a} at index 0, \say{b} at index 1 and \say{c} at index 2.

\begin{figure}[tbp]
  \input{figs/primdata_linkedlist.tex}
  \caption{Structure of a linked list.}
  \label{fig:primdata:linkedlist}
\end{figure}

% head and tail
That figure looks a bit like a snake. Let's briefly go back to the part where each link contains a payload and a reference. As you traverse a linked list you get a series of links representing shorter and shorter lists. We refer to the payload of such a link as the \defi{head}{Linked list!Head}, and the reference of it as the \defi{tail}{Linked list!Tail}.

% lookup performance
The formula from section \ref{sec:data:array} will calculate the address of an element within an array. This costs a multiplication, an addition and a \idx{memory read}{Memory!Read operation}. Notice that this is independent of the actual index. To look up a value in a linked list, we need to follow the chain. If the value is at index $n$, then we need to perform $n$ memory reads and -- depending on implementation -- a bit more. Memory is slow compared to additions and multiplications, so looking up a single value is a lot faster in an array. Looking up all values, if implemented the right way -- is very comparable in \idx{performance}{Performance} though.

% flexibility
Unlike arrays, it is possible to prepend elements to a list, and tails can be shared between list. Like with arrays, it is possible to create multidimensional linked lists. This is rarely done though. So, linked lists are more flexible than arrays and we pay for that flexibility by \idx{trading}{Tradeoff} execution speed.

\subsection{State Machines}

% what: a state machine is a way of structuring the flow of a program, think of it as a graph consisting of states in the form of nodes and transitions between those states in the form of edges, at any given time the machine will have one active state, each outgoing edge is associated with some event that will cause that transition to be followed, this updated the active state, upon arrival at a state some code is executed, state machine are typically used to process streams of inputs
A \defi{state machine}{State Machines} is a way of constructing the flow of a program (or part thereof). Think of it as a \idx{graph}{Graph} consisting of states in the form of nodes and transitions between those states in the form of edges. At any given time, the machine will have on active state. Each outgoing edge is associates with some event that will cause that transition to be followed and the active state to be updated. Upon arrival at a state, some code is executed. State machines are typically used to process streams of inputs.
